## Per-dataset findings requiring explanation (not exclusion)

### `authorization_decisions.csv`: `tx_id` missing for 46,152 rows, duplicated (blank) for 46,151

Investigated by cross-tabulating missingness against `operation`:
`ReadAudit`, `ReadEnvironmentalRecord`, `ReadProvenance`, `ReadSensorData`
and `ReadZone` rows are missing `tx_id` in essentially 100% of cases;
`ControlZone` in ~8.5%; `WriteSensor` in ~0.4%. This is consistent with
read-oriented `CheckAccess`-style operations not being recorded against a
distinct Fabric transaction id in this trace, rather than a data-corruption
problem. **No rows excluded**; the field is simply not populated for most
non-write operations, and no manuscript claim depends on `tx_id` being
present for those rows.

### `revocation_stages.csv`: `event_id` duplicated for 68 of 200 rows

`event_id` is not a per-row-unique key; it groups multiple lifecycle-stage
rows belonging to the same subject. Verified: 200 rows map to exactly 132
distinct `event_id` values, and 132 distinct `cert_user_id` values, with a
1:1 correspondence between the two (see `DATA_PROVENANCE_REPORT.md`). This
is expected structure, not a duplication defect. **No rows excluded.**

### `revocation_stages.csv`: no stage carries all four stage types for any subject

0 of 132 subjects have all four of {`publish`, `gossip`,
`propagation_complete`, `cache_invalidation`}; 87 have exactly one. This is
reported as a genuine finding (Sec. 6.9.4 of the manuscript, Limitation L5),
not treated as missing/corrupted data requiring exclusion, since it reflects
what the historical instrumentation actually captured.

## Sensitivity analysis

Given zero negative/zero/out-of-range values and zero duplicate complete
rows across every dataset, no sensitivity analysis excluding "questionable"
records was run for the field or controlled-experiment datasets; there were
no questionable records by the checks above. The one place a sensitivity
check was scientifically warranted -- the peer-scaling campaign's extreme
runs -- is reported in the main analysis
(`analysis/outputs/03_peer_scaling_results.json`,
`sensitivity_trim_extremes_total_latency`), not here, since it concerns
statistical robustness rather than data quality.
